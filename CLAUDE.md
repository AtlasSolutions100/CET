# CLAUDE.md — Takeoff Detection Engine

Read README.md for architecture. This file is the working contract: how to
test, how to report, and what not to assume. These rules override habit.

---

## 1. Verification protocol — non-negotiable

A detection or rendering change is NOT done on unit tests, engine JSON, or
overlay PNGs alone. Those are inputs to the diagnosis, never the proof.

Proof of a fix requires all three, every time:

1. The live app in a browser, driven through the flow a client actually
   uses: open the PDF -> Detect -> read the style list / legend panel ->
   inspect the canvas. (`./run-service.sh`, then http://localhost:8100;
   or the TakeoffDraft2 app when the claim is about import/render there.)
2. A screenshot of the full canvas AND a zoomed crop (>=400%) of the exact
   region being claimed fixed.
3. The same region cropped from the source PDF, side by side with (2).

Additionally, verification screenshots sent to the human are ANNOTATED:
circle every defect you found (and every region you checked and found clean,
mark sparingly) directly on the image before sending — the human must see
that you see what they see. And verification is a CRAWL, not a glance:
isolate the style(s) under test with the app's own filters so unrelated
linework is hidden, then zoom and pan across the whole sheet region by
region comparing render to original for completeness (missed pieces) and
placement (mis-boxes). A full-canvas screenshot alone is not a review.

Verification is not a claim, it is an artifact. Write every verification set
to `out/verify/<YYYY-MM-DD>/<topic>/` — the screenshots, the source crops,
and a `VERIFY.md` naming the sheet, page index, region, and what was
compared. "I screenshot-verified it" without that folder does not count.

If the browser and the engine JSON disagree, **the browser is the truth and
the gap is a bug to file** — the engine can be right while the UI renders it
wrong, and that has already happened (see the legend-swatch case in §5).

Never claim a page or feature is "working" from an overlay PNG. The overlay
is generated by the same code being tested.

## 2. The accuracy contract

Do not state an accuracy figure without all three of:

- **ground-truth source** (CAD layer names / hand-asserted truth map /
  human-confirmed count — say which)
- **expected count or length**
- **detected count or length**

A percentage with no denominator is a failed report. "100%" is almost never
true and saying it destroys trust in every other number in the message.

When a metric looks perfect, state what the metric *cannot* see. When it
looks bad, state whether it is a real miss or a metric artifact — and prove
which by eye before claiming "artifact" (this codebase has several genuine
artifacts, e.g. fence X-marks, and that history makes "artifact" too easy a
reach).

Ground truth for a sheet lives in `ground-truth/<sheet>_p<N>.json` once a
human has confirmed it. If a sheet has no ground-truth file, say so, and
propose the counts for the human to confirm rather than inventing a score.

## 3. Scope discipline

One objective per turn.

If a message contains several asks, **restate them as a numbered list at the
top of your reply**, do the first (or the one explicitly marked primary), and
list the rest as DEFERRED with a one-line note each. Never silently drop an
ask, and never half-do four things.

For anything non-trivial: **diagnose first, stop, and report before writing
fix code.** A diagnosis report is a table of pipeline stages with actual
measured values at each stage and a single highest-confidence root cause.
Wait for approval before the fix, unless the message says "diagnose and fix".

"Stop and report", "no fix code yet", and "diagnose only" are hard stops.
Landing a fix inside a diagnose-only turn is a process failure even when the
fix is correct, because it removes the only checkpoint where a wrong
hypothesis can be killed cheaply. If you believe the fix is obvious and
trivial, say so and still stop.

Answer every question that was asked. If a lettered/numbered question in the
request is not answered in the reply, name it as UNANSWERED with a reason.

## 4. Domain guardrails — the human is not a construction estimator

The owner of this project has not worked in HVAC, plumbing, civil, or
earthwork. He cannot catch a fabricated industry convention, so do not
create one.

- When a fix depends on a drafting or estimating convention (linetype
  meanings, LTSCALE, contour intervals, hatch conventions, trade
  abbreviations, units), **state the convention in one plain sentence and
  say where it came from**: this sheet's legend / general CAD practice /
  inference. Label inferences as inferences.
- Prefer evidence from the sheet itself over industry priors.
- Plain-English glossary line for any abbreviation the first time it appears
  in a reply (e.g. "SD = storm drain").

## 5. Known traps (learned the hard way — do not re-derive)

- **LTSCALE / PSLTSCALE.** A legend swatch is usually paper-space geometry
  and the plan linework is model-space, so the *same* CAD linetype prints
  with different absolute dash lengths in the legend than in the drawing.
  Match legend to plan on a **normalized dash:gap ratio signature**, never on
  absolute lengths.
- **Pattern order is information.** `dashArray()` in `webui/app.js` sorts
  dash lengths descending ("longest mark first"). That discards the true
  cadence order — a long-dash/short/short/long pattern cannot be
  reconstructed from a sorted list. Before touching dash rendering, check
  whether the ordering loss is the bug.
- **The legend swatch does not render a dash pattern at all.** In
  `webui/app.js` the style-row swatch is a solid 14x14 color chip
  (`sw.style.background = cssColor(s.color)`), styled in `webui/style.css`.
  The canvas path uses `ctx.setLineDash(...)`; the swatch path never does.
  Any "the legend shows a straight line" report is this, not a detector bug.
- **Coordinate spaces.** `get_drawings()` returns raw unrotated page
  coordinates; `get_text()` / `get_pixmap()` are rotation-aware. See README.
- **README "State (2026-08-17)" is stale.** `git log --oneline` is the truth
  about what has landed. FINDINGS-*.md is the current open-issue list.
- **Page numbering is ambiguous.** The human says "page 4" meaning the
  printed sheet; the engine indexes from 0 and output filenames use `_pN`.
  Always restate both: "engine page index 3 = printed sheet 4".

## 6. Tuning discipline

Tuning constants live in `chain.py` with rationale comments. Change them
against `takeoff_engine/batch.py` summary output across the corpus, never
against one sheet. Any constant change reports before/after on at least the
5-sheet milestone corpus, and names which sheets regressed.

The same gate applies to anything in the shared render or chain path — a
change to how dash templates are measured or drawn affects every style on
every sheet, not just the one that motivated it. Run the gate BEFORE
committing, not after, and report which sheets moved in both directions.

A pattern template measured from a single chain is a sample, not a
convention. State how many independent instances it was measured across and
whether they agreed.

## 8. Session hygiene

At the end of any turn that changes behaviour, append one line to
FINDINGS-<date>.md or the commit message that a fresh session could use to
pick up: what changed, what it fixed, what is still open. Assume the next
session has none of this context.
