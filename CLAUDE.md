# CET — general-construction takeoff (this repo)

**What this is.** A fork of the CORE Takeoff detection engine
(`Takeoff Automation/detection-engine`, branch `dev` at 8fb1fdb, forked
2026-09-08) that ships as its own product for the *building* side of a bid:
symbol counts (fixtures, grid bubbles), door and window marks against the
schedule, callouts, legend sheets, and - the first thing to build here - the
**flooring calculator** (room areas by floor type plus wall length, with the
room boundary bridged across doorways). The excavation product stays in the
original repo; the two share the detection engine and nothing else.

**How the split works.** `TAKEOFF_PRODUCT=construction` (the default in
`run-service.sh` here) makes `/api/config` say so, and `webui/app.js`
`applyProduct` hides the excavation calculators - Earthwork, Trench,
Structure - from the Tools menu and names the product CET. The code for
those panels is still in the tree on purpose: the regress gates and the
shared detection path do not fork, and a change to `chain.py` here should
be able to land there. Delete nothing that the gates hash.

**Its own everything.** Port **8300**, job store `C:/Users/kobys/cet-jobs`,
its own `.venv` (built with `uv venv .venv --python 3.12`), no git remote
yet (create the GitHub repo and `git remote add origin ...` when ready; the
excavation remote was deliberately removed so a stray push cannot land
there). `.env` was copied from the engine: the same UI password and LLM
keys.

**Run.** `bash run-service.sh` then http://localhost:8300 (any username,
the UI password from `.env`). `python -m takeoff_engine.regress --check
--require` before committing anything that touches detection.

**Roadmap (from the 2026-09 meeting; see the memory note "flooring
calculator ask").**
1. Flooring calculator - room polygons from wall lines, doorway bridging,
   floor-type from the finish schedule / legend, area by type + wall LF.

   schedule table (`marks.py` reads schedules already; the reconciliation
   view is the new part).
3. Symbol counting as a first-class panel with per-sheet and whole-job
   rollups (exists under Tools -> Count / Whole job; needs the same
   evidence discipline as the excavation panels).
4. Pricing memory and calculators per the boss roadmap.

Everything below this line is the engine's own contract and still binds.

# CLAUDE.md — Takeoff Detection Engine

Read README.md for architecture. This file is the working contract: how to
test, how to report, and what not to assume. These rules override habit.

---

## 1. Verification protocol — non-negotiable

A detection or rendering change is NOT done on unit tests, engine JSON, or
overlay PNGs alone. Those are inputs to the diagnosis, never the proof.

Proof of a fix requires all three, every time:

1. The live app in a browser, driven through the flow a client actually
   uses: open the PDF -> Detect -> read the style list / legend panel ->
   inspect the canvas. (`./run-service.sh`, then http://localhost:8100;
   or the TakeoffDraft2 app when the claim is about import/render there.)
2. A screenshot of the full canvas AND a zoomed crop (>=400%) of the exact
   region being claimed fixed.
3. The same region cropped from the source PDF, side by side with (2).

Additionally, verification screenshots sent to the human are ANNOTATED:
circle every defect you found (and every region you checked and found clean,
mark sparingly) directly on the image before sending — the human must see
that you see what they see. And verification is a CRAWL, not a glance:
isolate the style(s) under test with the app's own filters so unrelated
linework is hidden, then zoom and pan across the whole sheet region by
region comparing render to original for completeness (missed pieces) and
placement (mis-boxes). A full-canvas screenshot alone is not a review.

The FINAL deliverable of every review run — including batch sends of
multiple sheets — is the ANNOTATED comparison: every capture sent to the
human carries its circles (defects, improvement areas, and sparse clean
checkmarks) BEFORE it is sent. Raw captures without annotation are working
files, not deliverables; sending them as the review output is a process
failure even when the captures themselves are fine.

Verification is not a claim, it is an artifact. Write every verification set
to `out/verify/<YYYY-MM-DD>/<topic>/` — the screenshots, the source crops,
and a `VERIFY.md` naming the sheet, page index, region, and what was
compared. "I screenshot-verified it" without that folder does not count.

If the browser and the engine JSON disagree, **the browser is the truth and
the gap is a bug to file** — the engine can be right while the UI renders it
wrong, and that has already happened (see the legend-swatch case in §5).

Never claim a page or feature is "working" from an overlay PNG. The overlay
is generated by the same code being tested.

## 2. The accuracy contract

Do not state an accuracy figure without all three of:

- **ground-truth source** (CAD layer names / hand-asserted truth map /
  human-confirmed count — say which)
- **expected count or length**
- **detected count or length**

A percentage with no denominator is a failed report. "100%" is almost never
true and saying it destroys trust in every other number in the message.

When a metric looks perfect, state what the metric *cannot* see. When it
looks bad, state whether it is a real miss or a metric artifact — and prove
which by eye before claiming "artifact" (this codebase has several genuine
artifacts, e.g. fence X-marks, and that history makes "artifact" too easy a
reach).

Ground truth for a sheet lives in `ground-truth/<sheet>_p<N>.json` once a
human has confirmed it. If a sheet has no ground-truth file, say so, and
propose the counts for the human to confirm rather than inventing a score.

## 3. Scope discipline

One objective per turn.

If a message contains several asks, **restate them as a numbered list at the
top of your reply**, do the first (or the one explicitly marked primary), and
list the rest as DEFERRED with a one-line note each. Never silently drop an
ask, and never half-do four things.

For anything non-trivial: **diagnose first, stop, and report before writing
fix code.** A diagnosis report is a table of pipeline stages with actual
measured values at each stage and a single highest-confidence root cause.
Wait for approval before the fix, unless the message says "diagnose and fix".

"Stop and report", "no fix code yet", and "diagnose only" are hard stops.
Landing a fix inside a diagnose-only turn is a process failure even when the
fix is correct, because it removes the only checkpoint where a wrong
hypothesis can be killed cheaply. If you believe the fix is obvious and
trivial, say so and still stop.

Answer every question that was asked. If a lettered/numbered question in the
request is not answered in the reply, name it as UNANSWERED with a reason.

## 4. Domain guardrails — the human is not a construction estimator

The owner of this project has not worked in HVAC, plumbing, civil, or
earthwork. He cannot catch a fabricated industry convention, so do not
create one.

- When a fix depends on a drafting or estimating convention (linetype
  meanings, LTSCALE, contour intervals, hatch conventions, trade
  abbreviations, units), **state the convention in one plain sentence and
  say where it came from**: this sheet's legend / general CAD practice /
  inference. Label inferences as inferences.
- Prefer evidence from the sheet itself over industry priors.
- Plain-English glossary line for any abbreviation the first time it appears
  in a reply (e.g. "SD = storm drain").

## 5. Known traps (learned the hard way — do not re-derive)

- **LTSCALE / PSLTSCALE.** A legend swatch is usually paper-space geometry
  and the plan linework is model-space, so the *same* CAD linetype prints
  with different absolute dash lengths in the legend than in the drawing.
  Match legend to plan on a **normalized dash:gap ratio signature**, never on
  absolute lengths.
- **Pattern order is information.** `dashArray()` in `webui/app.js` sorts
  dash lengths descending ("longest mark first"). That discards the true
  cadence order — a long-dash/short/short/long pattern cannot be
  reconstructed from a sorted list. Before touching dash rendering, check
  whether the ordering loss is the bug.
- **The legend swatch does not render a dash pattern at all.** In
  `webui/app.js` the style-row swatch is a solid 14x14 color chip
  (`sw.style.background = cssColor(s.color)`), styled in `webui/style.css`.
  The canvas path uses `ctx.setLineDash(...)`; the swatch path never does.
  Any "the legend shows a straight line" report is this, not a detector bug.
- **Coordinate spaces.** `get_drawings()` returns raw unrotated page
  coordinates; `get_text()` / `get_pixmap()` are rotation-aware. See README.
- **README "State (2026-08-17)" is stale.** `git log --oneline` is the truth
  about what has landed. FINDINGS-*.md is the current open-issue list.
- **Page numbering is ambiguous.** The human says "page 4" meaning the
  printed sheet; the engine indexes from 0 and output filenames use `_pN`.
  Always restate both: "engine page index 3 = printed sheet 4".

### Four code shapes that produce silent wrong numbers

Seven defects have traced to these. None crashed, none moved the gate, each
was found only by staring at one sheet - which in a takeoff tool is the
worst kind, because a confident wrong number reaches a bid.

- **A proximity test is not a bucket.** `round(x / TOL)` answers "which
  bin", NOT "are these two within TOL of each other". Two things 6.8 pt
  apart land in different bins whenever an edge falls between them, and
  widening TOL just moves the edge. That is what shipped Beaumont's Barn
  civil C4.3 footer drain labelled `> > >`: `read_legend`'s 7.0 pt row
  bucket put the flow chevrons (cy 469.4) and their description (cy 476.2)
  on opposite sides of an edge, so the sheet's most valuable item -
  1,449.6 ft of perimeter drain, $31/ft on the client's own Estimate #853 -
  lost its name. Same shape: the schedule reader never once found a
  QUANTITY column on a skewed scan, and a spot-grade dedup double-counted
  12 labels. **Fix: sort and walk with a gap test, or a radius test for
  dedup.** A bucket is only legitimate as a *fingerprint* - a key both
  sides of the comparison share, used to count repeats, where the edge can
  only split a family and never merge two. `eval_layers._congruence_groups`
  is one and was measured to be one (7,583 layers, identical verdicts, and
  a gap-walk there is strictly worse); `marks.size_families` is one only
  because a radius test does the real work one line later. Prove which kind
  you have before touching it.
- **First-writer-wins discards the right answer.** `dict.setdefault(k, v)`
  keeps whatever arrived first and drops the rest with no ranking and no
  record. `read_legend` had ALREADY computed
  `PROPOSED 4" RIGID PERFORATED PVC FOOTER DRAIN PIPE` and joined it to the
  right style, then lost it to a chevron that got there first - and because
  a legend label overwrites the CAD layer name, the output was worse than
  if the legend had never been read. Any either/or needs an **explicit
  ranking** (`legend_detect._assign_label`: an unusable label never wins, a
  usable one replaces an unusable one), and where no honest ranking exists,
  keep the alternatives visible and abstain rather than pick silently -
  `ScaleResult.candidates` returns every reading with its context. (An
  `areas.page_areas` change to abstain on a fill two legend rows contest
  was HELD at review: its "provably no-op over 2,059 pages" claim was a
  truncated run - the corpus is 6,724 pages and the change moves 40 of
  them. A silent cap reports as full coverage; say what you skipped.)
- **0.0 is not None.** `x.ink or x.length` reads measured-zero as
  unmeasured, because `0.0` is falsy. An attempted zero-ink guard built on
  that assumption deleted 80% of every sheet's chains; the gate caught it
  on the first run. Measured on C4.0 p0 (1,429 chains): **1,157 carry
  `.ink == 0.0` and not one carries `.ink is None`** - 196 of those are
  ordinary `solid` lines and they hold 44.7% of the sheet's chained length.
  `.ink` is populated only for dash chains, so the `or` fallback is the
  intended read and anything treating zero as "no ink" is deleting solid
  linework. Test `is None`, never truthiness, and say which you measured.

- **What you extracted is not what is printed.** A ranker can only see the
  candidates a reader managed to recover, and it has no way to know which
  ones the reader dropped. "The single surviving value" therefore is NOT
  "the single printed value" - it can be sampling bias wearing the costume
  of an uncontested answer, and **no filter over the recovered text can
  detect it**, because the evidence that would refute it is exactly the
  evidence that failed to arrive. Measured 2026-09-01 on Hurricane C.3.5,
  which prints THREE scales - HORIZ 1" = 40', VERT 1" = 10', and a key map
  at 1" = 300'. OCR recovered only the key map, so an otherwise sound
  ranker picked 300 as a clean uncontested single: 7.5x wrong, silently.
  On Thielen ID-1.04 the same pass ate the trailing `0"` of `1/4" = 1'0"`
  and produced 40 where the truth is 4 - 10x, and volume moves with the
  SQUARE of scale, so 100x in cubic yards. **Fix: when the recovery step is
  lossy, abstain and keep the candidates visible rather than promote a
  winner.** A disclosed-but-wrong default still anchors the operator; a
  disclosure tells someone to be careful, a populated field tells them the
  answer. `ScaleResult.candidates` exists for exactly this. Every reader
  here that picks a best from what it managed to extract - legend, schedule,
  spot tags, inline labels - has this hole; check yours before ranking.

## 6. Tuning discipline

Tuning constants live in `chain.py` with rationale comments. Change them
against `takeoff_engine/batch.py` summary output across the corpus, never
against one sheet. Any constant change reports before/after on at least the
5-sheet milestone corpus, and names which sheets regressed.

The same gate applies to anything in the shared render or chain path — a
change to how dash templates are measured or drawn affects every style on
every sheet, not just the one that motivated it. Run the gate BEFORE
committing, not after, and report which sheets moved in both directions.

A pattern template measured from a single chain is a sample, not a
convention. State how many independent instances it was measured across and
whether they agreed.

## 7. Commands

```bash
./run-service.sh                                   # review UI on :8100
python -m takeoff_engine.cli "<plan.pdf>" --page 0 --out out
python -m takeoff_engine.batch "<plans-dir>" --out out/batch
python -m takeoff_engine.sweep ...                 # broad-corpus sweep
python -m takeoff_engine.milestone_report          # evidence pack -> out/milestone

# BOTH gates, before committing anything that touches detection or volumes.
# --require makes a truth case whose inputs are missing a FAIL instead of a
# visible SKIP: on this machine and on the production box every input IS
# present, so a skip there means something moved, not that a fixture is
# absent. Set EARTHWORK_REQUIRE=1 in the production environment for the
# same reason (the subprocess inherits it).
python -m takeoff_engine.regress --check --require
```

## 8. Session hygiene

At the end of any turn that changes behaviour, append one line to
FINDINGS-<date>.md or the commit message that a fresh session could use to
pick up: what changed, what it fixed, what is still open. Assume the next
session has none of this context.
