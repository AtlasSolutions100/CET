## F80 — DEAD HYPOTHESIS: `build_chains` colour/width grouping is NOT the raster loss

**Do not re-chase this.** It was the leading raster theory for a day and it is wrong.

The theory: `build_chains` partitions stroke units by `(colour, width, layer)` *before*
linking, and on raster input that key is an estimate recovered from pixels, so one
wrong bucket is unrecoverable.

The test: bypass the partition entirely — one bucket for every unit, the absolute
ceiling of any grouping fix. Truth source: each sheet's own vector-path chains;
denominator truth ink-mark length (belle 79,641.1 pt, c80 180,807.5 pt).

| case | as-is | one bucket | delta | loss available | class agreement |
|---|---|---|---|---|---|
| belle clean | 89.5% | 89.5% | -0.0 | 7.6 pp | -5.5 |
| belle degraded | 81.6% | 83.0% | **+1.4** | 7.6 pp | -8.1 |
| c80 clean | 76.4% | 76.1% | -0.3 | 18.7 pp | -13.0 |
| c80 degraded | 73.1% | 71.2% | -1.9 | 17.9 pp | -16.5 |
| c40 clean | 71.8% | 69.2% | **-2.6** | 20.0 pp | -7.1 |
| c40 degraded | 63.2% | 65.1% | **+2.0** | 22.2 pp | -13.6 |

**Mean -0.25 pp. Up in 2 of 6. Class agreement falls in all six.**

Three reasons it is dead, not merely unproven:

1. **The ceiling is at or below the floor.** The two positive cases recover <=18% of the
   available loss while giving up 8-14 pp of agreement.
2. **The partition is not a one-way loss.** On c80 clean, removing it recovers 5,644
   truth-ink samples and destroys 5,381. A softer bucket is the same trade sampled
   finer — it cannot escape this.
3. **The original evidence had already been consumed.** The 9->18 colour scatter and the
   dash1 72.8->20.7 collapse were measured on `base`. The colour fix shipped in the same
   session (`380371a`) collected them. The handoff extrapolated that evidence onto the
   post-fix residual; this run tests the extrapolation directly and it fails.

No fix proposed and none warranted. Next step is to split the residual by **drop
mechanism** (never linked / under `MIN_DASHES` / pruned as hatch / pruned as text /
demoted to annotation) before touching chain-side code.

**A denominator problem to settle first.** On C8.0 the sheet number "C8.2" is drawn as
**vector letter outlines**; the vector path chains those glyphs into the truth
denominator while the raster path correctly declines them — **both sides miss them
identically**. Part of what we read as raster loss is a measurement artifact. Confirmed
by eye on two crops, share not quantified. Routed to the gate work.

## F83 — Filled areas are invisible to the engine; five legend rows collapse to one style [OPEN, HIGH VALUE]

Koby found this in the live app: on Barn civil the legend rows **PROPOSED CONCRETE**,
**PROPOSED PATIO AREA**, **PROPOSED WALKING PATH**, **PROPOSED WATER FEATURE** and
**EXISTING MAPPED WETLANDS** all report the same style, `SE-P-CONC`, even though the
legend names them separately and several are distinguished by their fill.

Diagnosed on `SWR_Barn_Residence_-_Civil_4.7.26.pdf` engine page index 1. Three
distinct defects, in increasing order of depth.

**A. The legend swatches genuinely are one layer.** Every swatch outline in that column
is on the single CAD layer `SE-P-CONC` at black w0.6-0.72. The drafter drew the legend
boxes on one layer because in paper space the layer means nothing. So the engine's
style assignment is *correct about the geometry* and useless to the estimator. A legend
row's identity is its adjacent TEXT, never its geometry.

**B. The engine is fill-blind.** From `get_drawings()` on that swatch column:

| legend row | outline | fill |
|---|---|---|
| PROPOSED CONCRETE | black w0.6 | none |
| PROPOSED PATIO AREA | black w0.6 | none |
| PROPOSED WALKING PATH | black w0.6 **dashed** | none |
| PROPOSED WATER FEATURE | black w0.6 | **grey 0.592** |
| EXISTING MAPPED WETLANDS | black w0.6 | **blue** |

Four of the five carry an identical outline; the fill is the only appearance
discriminator. `extract.py` builds `fill_rects` (line ~225) and exposes `fill_boxes()`
(line ~368), but uses them for exactly one thing: marking a near-white stroke that sits
on a darker fill (`on_fill`). **`on_fill` is True for 7 of 936,044 units on this page.**
The fill itself is discarded and never becomes a chain, a style, or a takeoff row.

**C. A filled area is being measured in linear feet.** The live status bar reads
`solid · SE-P-CONC · 20 LF · 5 points` for a concrete swatch. Concrete, patio, water
feature and wetlands are **area** items — an estimator buys them in square feet (or
cubic yards once a depth is applied), never in linear feet. Today the engine can only
offer the perimeter.

CONCRETE and PATIO AREA have *identical* stroke and *no* fill, so appearance alone can
never separate those two — on the plan they must be separated by CAD layer, and in the
legend by their text. Any fix has to use all three signals: text for the name, fill for
the appearance match, layer for the plan geometry.

This is not specific to this PDF. Any site plan with hardscape, water features or
wetlands has the same structure, and it is a whole class of takeoff item — hardscape
areas — that the engine currently cannot quantify at all.

## F100 — The profile graticule: diagnosed, fix NOT landed, and the trap that stopped it

### The defect (diagnosis complete, high confidence)

Guide civil engine page 3, layer `34008 DE ACTIVITY BARN|C-ROAD-PROF-VIEW` carries
**2,948 strokes of which 2,656 are zero-length** — `[[x,y],[x,y]]`, one moveto/lineto to
the same point, stroke width **0.06 pt**. They form a 2-D lattice, **72 rows x 250
columns at 9.00 pt pitch**: the profile boxes' graticule. They do print — about 0.0008
inch of ink each — but they are not a line.

The chainer links them into **57 `dash1` chains, 10,286 pt, containing 0.00 pt of ink**,
which the live app bills as **1,429 LF** of dashed line, checkbox on by default: 3.85% of
the sheet's emitted span and **10.9% of its `dash1` footage**.

No single stage is at fault. Measured at stage boundaries: the stipple crowd guard uses a
6.0 pt radius against a 9.0 pt lattice so drops none; `_match_links` allows the 9 pt pitch
because median dash length is 0 so `max(12.0, 4*0)` is the floor, and `_out_dir` returns
the fallback `[1, 0]` for a stroke with no direction, so **every speck claims to point
+x** and the angle test is free; `_prune_junk` keeps 64; `_compound_merge` adds 1,843
stray dots on `has_dot`; `_stitch_across_styles` welds 73 into 57. **Three stages do the
same wrong thing because none of them asks whether the chain contains ink.**

`phantom_span_audit` **understates** it: 22 of the 57 are >=150 pt and only 19 flag; the
3 escapees run along a real axis and land on genuine ink.

### Layer guard rejected, with evidence

`C-ROAD-PROF-VIEW` carries **57 phantom chains (10,286 pt, 0 ink) AND 57 real
ink-bearing chains (25,883 pt span, 25,841 pt ink)** — the box frames, axes and grade
lines. A layer guard in the chainer would delete 2.5x more real geometry than fake. And
**23.2% of emitted chains gate-wide (1,457 of 6,275) carry no layer at all**; three of
the ten fast-gate sheets have none whatsoever. This is why `_NON_PLAN_LAYER` is right in
`earthwork.py` — "does a section view belong in a plan TIN" is a whole-view question —
and wrong in the chainer, where the question is only "is this line real".

### The threshold that would work

Ink recomputed from each chain's own mark partition across 17 sheets and ~16,400 chains:
lowest ink fraction of any genuine chain >=150 pt is **0.186**; 1st percentile 0.340;
median 0.676. **Between 0.000 and 0.186 the corpus is empty.** An exactly-zero test needs
no tuning constant. Zero-ink chains appear on 1 of 17 sheets.

### Why the fix is NOT landed — the trap

I implemented it against the `LineChain.ink` field and it **deleted 80% of every sheet**:
C4.0 1429 -> 249 chains, C8.0 573 -> 229, Belle 350 -> 85. Caught by the gate on the
first run and reverted.

**`.ink == 0.0` does not mean "no ink". It means "never measured".** On C4.0, **1,157 of
1,429 chains have `.ink == 0.0` and they are ordinary `solid` lines** with
`seg_counts = None` — a solid chain's ink IS its length and the field is simply never
populated for it. Only 272 chains carry a positive `.ink`.

So the `payload.ink or payload.length` idiom at `chain.py:92, 1879, 1949, 2078, 2191,
2235, 2302, 2619, 2620, 2705` is **load-bearing and correct**, not the bug it resembles.
It is misleading in exactly one case — a chain built from zero-length specks, where 0.0
genuinely is zero — and that case cannot be told apart from the other 1,157 by reading
the field.

**The real fix therefore needs a measured ink figure, not the `.ink` field**: recompute
from each chain's own mark partition (as the diagnosis did to produce the 0.186 census),
or separate "unmeasured" from "measured zero" by initialising `ink` to `None` and setting
it wherever a chain is minted. Both are larger changes than they look, and neither should
be attempted without re-deriving the census first.

**Recorded as the clearest reminder tonight of why the gate runs before the commit.** The
diagnosis was right, the threshold was right, the evidence was right, and the field I
reached for was the one the diagnosis had explicitly said not to trust.

## F131 — Scope filter: a view was writing itself into the record, and 78% of the sheet vanished [FIXED, live re-test PENDING]

**What the feature is.** "Declare your trades" lets the operator say *I only do

## F132 — Nothing survived closing the tab, and it was one Map [FIXED, live re-test PENDING]

Item 2 of the six. Every reviewer decision in the app — labels, prices, trade
assignments, quantity overrides, typed scales, which rows are ticked, LF-vs-EA
— went through a `store` object whose entire backing was `const sessionMem = new
Map();`, plus a loop that actively *deleted* any saved work an earlier build had
left in `localStorage`. Close the tab, lose the evening. On a 15-sheet set that
is the difference between a tool and a demo.

**It was deliberate,** and the reason was good: with nothing kept, a reloaded
seat and a brand-new seat produce byte-identical output, so nothing in a client
demo can be pre-baked. That is the demo-integrity rule, and it is worth keeping.

**But they are not the same requirement.** Demo integrity says *a document
nobody has touched must read empty*. Usability says *my edits to my document
must still be here tomorrow*. Both hold at once if memory is (a) written only by
an operator action, (b) scoped to the document, (c) never seeded, and (d)
visibly clearable. Nothing is pre-populated, so an untouched document still
reads exactly as a fresh seat does.

**What landed.**

- `store` is now backed by `localStorage` under a schema prefix `MEM_V = "tk1::"`,
  mirrored in the same `Map` so reads stay synchronous and semantics do not move.
  Only a *changed* value reaches the disk — renderers re-save what they just
  read, and without that guard one price keystroke on a 73-row sheet is 73
  writes of an unchanged string.
- `MEM_V` is load-bearing. The old comment correctly noted that a key-shape
  change cannot catch a reviewer mid-session while the store dies with the page.
  Once memory outlives the page that guarantee is gone, so **any key-shape change
  must bump `MEM_V`** — superseded versions are never read and are purged on load.
- `store.setSession(k, v)` — writes the mirror, never the disk. The two places
  that file rows under "Earthwork & Grading" are the *app* choosing a default,
  not the operator making a choice; one of them already said so in a comment
  ("Session default only - the reviewer's own trade pick wins"). Persisting an
  app-chosen default makes it indistinguishable from a decision: it survives a
  clear, it inflates the count, and it silently outranks a better default later.
  Exact sibling of `setIncludeTransient` from F131, same lesson.
- Private windows and a full quota are handled by *saying so*, not by pretending:
  the button turns amber and its tooltip states that the work is session-only.

**The demo control (asked for explicitly).** A `Saved work · N` button appears in
the header only when N > 0 — an untouched seat shows nothing at all. It opens a
two-item menu, because conflating these destroys either an evening of pricing or
a demo:

| action | clears | leaves |
|---|---|---|
| **Reset this document · N** | this PDF's decisions **and the service's cached detection for it** | shared price list, trade assignments, other documents |
| **Forget everything · M** | all decisions everywhere, including shared prices/trades | cached detections |

The server half is new: `POST /api/job/{job_id}/reset` deletes every derived
artifact in the job's own directory — results, page renders, elements, earthwork
maps, callouts, symbols, schedules, report PDFs — and clears the in-memory status
map so the UI must detect again. **Clearing the browser alone was not enough for
a real demo:** the service serves `p<N>_result.json` straight back, so a "fresh"
run in front of a client would replay a result computed hours earlier. That is a
pre-warmed cache presented as a live run.

Source PDFs are never inside the job directory (a sample opens by path, an upload
is written to a *sibling* `upload_<hex>_<name>.pdf`), and the guard re-derives the
directory from `JOBS_DIR` and refuses anything that is not a direct child, so a
crafted `job_id` cannot walk out of the jobs tree.

**Verified in-process** (17/17; `httpx` is absent from the venv, so the route
function is called directly rather than over HTTP): traversal rejected for `..`,
`../..`, `<job>/..`, and unknown ids; 13 of 13 artifact kinds removed; job
directory survives and is empty; **sibling PDF untouched**; registry entry
survives; status map cleared; a second reset is a no-op, not an error.

**STILL OPEN — the live re-test.** None of the browser half has been driven on
:8100; the pane wedged the operator's machine. Needs, in one pass alongside
F131's scope sequence: edit → close tab → reopen → edits present; an untouched
document shows no button; Reset this document → cold detect; Forget everything →
fresh seat; private window → amber button and an honest tooltip.

## F136 — A quantity the operator typed never reached the deliverable [FIXED, verified end to end]

The worst defect in the app, and the one the harm ranking is written for: a
confidently wrong number reaching a bid with no symptom on screen.

**What happened.** An operator corrects a quantity. The itemized panel shows the
correction. The trade subtotal shows it. The TOTAL shows it. The CSV shows it.
`p<N>_elements.json` and the **Report PDF — the only thing that goes to the
client — show the detector's original**, under the same line-item name, with no
warning anywhere.

Measured on Barn Civil printed sheet 3, one row, priced at $10/ft:

| | on screen | in the report, before | in the report, now |
|---|---|---|---|
| PROPOSED CONTOUR (legend) | 18,000.0 ft | 25,027.8 ft | **18,000.0 ft** |
| extended | $180,000 | $250,278 | **$180,000** |

**$70,278 on one row of one sheet**, silently.

**Root cause — CLAUDE.md §5 shape B, as an architecture rather than a line.**
`computeTakeoffRows()` exists precisely because "one computation for the itemized
panel AND the CSV export" was the right answer. The approve payload never called
it. It was a second, hand-maintained re-derivation assembled field-by-field from
raw state, and **every fact it forgot to consult became a silent divergence**.
Three holes, not one:

- a typed FOOTAGE override: no field for `ovKey(label, "ft")` existed at all
- an EA override on a SYMBOL-COUNT row: `object_counts` only walks
  `state.result.styles`, and a symbol mark is an `extraItems` entry
- an override on a CALCULATOR row: `extra_items` spread `...it`, sending the
  calculator's raw qty

**The fix is structural, not a fourth copy.** The client now builds
`quantity_overrides` **from `computeTakeoffRows()` itself** — the same function
the panel and the CSV render from — so the payload cannot drift from the screen
again. `object_counts` goes back to meaning what its comment always said: the
DETECTED count. There is now exactly one field a reader consults to learn
whether a figure was measured or typed.

**Disclosure is not optional.** A bid document that cannot tell a measured
number from a typed one is the problem, not the solution. So:

- the item carries `length_ft` (billed), `engine_length_ft` (measured) and
  `qty_set_by: "reviewer"`
- the export carries a top-level `overrides` array, **written even when empty** —
  `[]` says "this export knows what an override is and has none", which a file
  predating the field cannot say
- the report PDF prints a banner above the table, stars the row, and prints
  `* set by the reviewer: 18,000.0 ft. Measured on this sheet: 25,027.8 ft.`
  under it; the summary page stars and reconciles the same way
- an override matching no row lands in `override_warnings` and turns the approve
  status line red, because a correction that silently failed to land is the very
  defect being closed

The per-chain geometry is deliberately **not** scaled to match. The chains still
measure what was drawn; the item says what is billed and what was measured. A
reader can reconcile them instead of guessing.

**Verified end to end** on :8100, Barn Civil printed sheet 3, 1,251 elements /
93 items: approve reports `1 quantity you typed is in the export and marked * on
the report`; `p2_elements.json` carries `length_ft 18000.0`,
`engine_length_ft 25027.8`, `qty_set_by reviewer`, `extended 180000.0`, and the
top-level `overrides` entry; the report PDF prints the banner, the starred row,
the reconciliation line, and the starred summary row.

**Left open, named:** `INTEGRATION.md` records that TakeoffDraft2's import route
reads `elements` and re-measures the polylines, so an override does not reach it
yet. It is carried in `items[]` and `overrides[]` for when that route is taught
to read them.

## F145 — Cut and fill are integrated over a convex hull, not the graded area [FIXED, opt-in]

The largest measured error in the product, reported independently by two
clients in one day.

**Jason Knudson (sitework), of a 172,094 CY read:** *"that 172,000 yards,
clearly that's off. But is that because you haven't put a boundary? Can we
boundary these?"* — and the requirement: *"an automatic boundary would be cool,
but it would have to be editable."*

**Josh Stice (mass grading, ~600 acres, 1" = 200')**, who scored us against his
own finished takeoff:

| | ours | his | |
|---|---|---|---|
| cut | 2.1M CY | 2.2M CY | within ~5% |
| fill | 2.6M CY | 1.6M CY | **1.0M CY over** |

His diagnosis, unprompted: *"it's filling all that stuff outside"*, *"it's got
the grading limit, right? Can you add that line?"*, *"that dash line around the
perimeter, I think that's the grading limits."*

**Confirmed in code.** `cut_fill` integrates where `ok = ~(isnan(ze) |
isnan(zp))` — wherever BOTH TIN interpolators are defined, which is the
intersection of the two surfaces' **convex hulls**. A hull cuts straight across
every bay and notch and reaches to the furthest contour, so on a concave or
sprawling site it covers ground nobody is grading. Cut survives because cut
happens inside the pad; fill does not, because the hull's overhang is where the
proposed surface sits above existing. The panel's own standing caveat already
admitted this — *"the region is not the graded area and nothing on this panel
can make it so"* — which is now false, in the good direction.

**Fix.** `cut_fill(..., boundary=None)` takes a limit-of-work polygon in page
points and ANDs a vectorised even-odd point-in-polygon test into `ok`.
Even-odd rather than winding, because a hand-traced limit sometimes doubles
back. Written against the whole grid in one pass: a per-cell Python loop over a
4-million-cell grid would take minutes.

**Opt-in by construction.** Passing `None` is not a handled special case, it is
the original code path untouched — verified: `boundary=None` returns values
identical to omitting the argument.

**Verified, synthetic** (100×100 ft site, proposed exactly 3 ft above existing,
so every figure is checkable by hand): no boundary → fill = area × 3 ÷ 27
exactly; half boundary → area ratio **0.5000**, fill ratio **0.5000**; L-shaped
boundary keeping three quadrants → **0.7500**, which a convex hull would have
reported as 1.0000. A 2-point boundary and a boundary that misses the site are
both refused with a reason rather than silently ignored.

**Verified, live and end to end** on Barn Civil printed sheet 3 — the one sheet
with a client estimate to check against, where the region was 317,632 SF versus
that estimator's own 224,058 SF of clear & grub:

| | no boundary | boundary from chain 3216 (503 pts) |
|---|---|---|
| region | 317,632 SF | 308,276 SF |
| cut | 13,677.4 CY | **9,806.9 CY** |
| fill | 40,349.6 CY | 39,900.5 CY |

The UI reports `chain 3216 — 503 points — 328,872 SF`, the request carries all
503, the response confirms `boundary_applied: true`, and the standing caveat
rewrites itself to *"Inside the limit of work you set… Ground outside it is not
counted at all."*

Chain 3216 is an unnamed dashed perimeter chosen as a plausible limit, **not a
line the sheet declares as one** — so the 28% drop in cut demonstrates the
mechanism, not a corrected quantity. The real validation is Stice's sheet, where
a true grading-limit line is drawn and his own numbers exist to score against.

**Still to build:** auto-suggesting the boundary from a chain whose layer or
label names a limit (GRADING LIMIT / LIMITS OF WORK / LOD / DISTURBANCE), and
drawing one by hand for sheets that print none — Jason's editable requirement.

## F148 — Both Caddy rationales were backwards [CORRECTED]

The full stack now runs: `docker compose up -d` brings up app + Caddy, Caddy
issues its own cert, HTTP 80 redirects to 443 with a 308, `/api/config` answers
401 without credentials and 200 with them, the UI serves 20,806 bytes, and a
17 MB plan set uploads through the proxy in 352 ms.

Then measuring the two proxy settings disproved the reasons I had written for
both of them. **Caddy's defaults are unlimited on both axes.**

| claim I shipped | measured |
|---|---|
| "Caddy's defaults would cut a long response off and show a reasonless 502" | stock Caddy proxied a backend that took **90 s to its first byte** and returned **200** — there is no default response deadline |
| "the default body limit would reject the upload" | stock Caddy accepted a **600 MB** body and passed **all of it** to the backend — there is no default limit |

So neither setting rescues anything from a default. Both are **ceilings I
imposed**. Kept, with the comments rewritten to say that, because one of them
turns out to matter for a reason I had not noticed:

`/api/upload` does `raw = await file.read()` — the **whole body lands in memory**
before a byte is written to disk. With no cap, one request pages out the box.
512 MB is roughly 10× the largest real plan set (stice is 17 MB). Verified on
the live stack: 600 MB returns **413**, the app container stays `running`,
`restarts 0`, `OOMKilled false`, and a 17 MB set still uploads 200 right after.
**Raising that number without changing that read is how the box falls over** —
now written next to the number.

The 30m socket timeout is kept as a bound on a silent socket, not as a rescue.
Detection is async (`POST .../detect` returns `{"status":"running"}` in ~1 s and
the UI polls), so the long-request risk was never there in the first place; it
is `report.pdf` across many approved sheets that runs long.

**One knock-on the measurement exposed.** A 413 is produced by Caddy, so there
is no app JSON to parse and `uploadPdf` fell through to a bare
`upload failed (413)` — precisely the reasonless failure I had claimed to be
preventing, except self-inflicted. `webui/app.js` now names both proxy-produced
statuses: 413 → *that plan set is too large — the limit is 512 MB per upload*,
401 → *signed out — reload the page and enter the password again*. Cache-buster

## F150 — seed-demo.sh, and the staleness rule it exists for

`./seed-demo.sh https://core.workoptional.studio` uploads the demo corpus from
a machine that has it and detects the pages worth showing. The set is not
arbitrary: every page is either one `takeoff_engine/regress.py` measures every
run (so we have evidence for its numbers) or one Koby named on 2026-08-25.
Klayton's fiber set is excluded by name and with the reason, because he is
under NDA.

The reason a script beats "upload them through the browser once": a stored
result records the `engine_sig` that produced it, and `_result_stale` refuses
to serve one whose signature has moved. So **the volume surviving a deploy
keeps the files but not their validity** — any deploy touching
`takeoff_engine/` silently un-warms the demo, and the only safe answer is to
re-seed. That is now stated in DEPLOY.md and at the top of the script.

Also in DEPLOY.md: full Hetzner provisioning, in dependency order, with the
one ordering constraint called out — the DNS record must resolve before the
first `docker compose up`, because Caddy requests the certificate on boot and
backs off after a failure.

### F150 measured

Full seed against a container at 4 workers / 12 GB, all 14 documents (188 MB
uploaded) and all 20 pages:

**cold: 20/20 detected, 0 failed, ~350 s.** Slowest sheets were SWR Barn
Structural p3 (44 s), C9.0 Road Layout (36 s), SWR Guide Civil p2 (36 s),
C4.0 Site Grading (31 s). Belle Farms sheets ran 5-10 s.

**warm re-run: 20/20, 0 failed, 6 s** — the idempotence claim, measured. So
re-seeding after an engine deploy costs about six minutes, and re-running it
when nothing changed costs nothing.

One note for whoever runs it next: the first run ended in a bash syntax error
that was **not the script**. The hostname was find-and-replaced in

## F153 — The healthcheck written to accept 401 could never accept 401 [FIXED]

The production container ran **28 consecutive failed healthchecks** while

was fine.

The Dockerfile's check was written specifically to treat 401 as healthy:

```

```

**`urllib.request.urlopen` raises `HTTPError` on a 401 rather than returning a
response**, so the `in (200,401)` line never executed. The check threw, exited
non-zero, and the intent encoded in that tuple was dead code from the day it

`RAISED HTTPError 401`.

tuple test actually runs and no exception handling is needed. A genuinely dead
app still fails, by refusing the connection. Verified: returns 401 -> exit 0,
and the container reports **healthy** after the rebuild.

This is the third instance of the same root error in this deployment work `-`
after the CI probe against `https://localhost` (F149) and the two Caddy
rationales (F148). Each time the mistake was **asserting how a tool behaves
instead of running it once**. The tuple `(200,401)` looks like the bug is
handled, which is precisely why nobody re-reads it.

## F159 — HTTP Basic removed; real login page and session cookies [FIXED]

Koby could not get into his own box. He was pasting a correct password and
still getting refused, and checked Docker to be sure. **The cause was HTTP
Basic itself.** A browser caches the credentials it was given for a realm and

credential. There is no sign-out for a Basic prompt and no way to clear it from

- HMAC-SHA256 over `{user, exp}`, key in `session.key` **beside the job

  cannot be used to find out which of twenty addresses has one.
- Crude per-IP throttle, 12 failures per 5 minutes.
- A **Sign out** button, which is the thing Basic could never have.

what Koby asked to do - would have removed authentication from a public box
rather than switching it over. The middleware is now always mounted and decides
per request, and **fails closed**: hosted with neither accounts nor a password

## F167 — The loading overlay was hung off the wrong signal; removed

Shipped in v1.6.0 and pulled the same day. It was triggered by
`setStatus(..., "busy")`, and **"busy" in this app means two different
things**:

| real work | an interactive prompt |
|---|---|
| `detecting...` | `structure: click a closed line that is the building outline` |
| `opening...` | `add contour: click the contour line on the sheet` |
| `Reading the sheet with AI...` | `cut: now click where the span ends` |
| `removing...`, `resetting edits...` | `draw: click points - Enter finishes` |

(and one that is neither: `this sheet was detected with an older engine`).

So arming any canvas tool threw a full-screen overlay over the drawing the
operator had just been told to click. Not merely ugly - **the tool could not be
completed.** Koby hit it on the structure tool within minutes of it going live.

The mistake was choosing a hook by how many call sites it covered (23) instead
of by what it means. The status line already reports both cases and blocks
nothing, which is why it was right all along.

Removed the overlay, its CSS and its markup; `setStatus` is back to the
one-liner. `lockup-animated.svg` is kept - it is a reasonable splash or
full-page-load asset - but nothing renders it today, and the CSS says why so
the next person does not re-hang it off the same signal.

Verified after removal: no fixed element over the sheet, the structure prompt
still reads on the status line, and the canvas is clickable.

## F168 — Room for other apps on the box: a conf.d socket and a shared network

A second project (Bison Lawn Care, on another domain) is going on this VPS. It
does **not** need extra ports: Caddy already owns 80/443 and routes by
hostname. It needs a DNS record and a site block.

Headroom, measured: **29 GB of 31 available**, takeoff actually using 1.4 GB
against its 24 GB ceiling; **384 GB of 387 disk free**; load 0.00 across 8
cores. The box is nearly idle.

**Two fragilities in the plan that agent proposed, both corrected here.**

1. It assumed the Caddyfile might sit in a git working tree and to check with
   `git status`. `~/takeoff` is **not a git repo** - the source was shipped by
   `tar` - so that check returns "not a git repo" and reads as an all-clear.
   The real hazard is worse and certain: **every deploy `scp`s `Caddyfile` and
   `docker-compose.yml` onto the box** (F160), so a hand-appended site block is
   guaranteed to be overwritten by the next takeoff release.
2. It proposed `docker network connect` on the live Caddy container. That works
   until anything recreates Caddy, at which point the attachment is silently
   gone and the other app 502s.

Both are solved by putting the wiring in this repo, where CI already ships it:

- `import /etc/caddy/conf.d/*.caddy` at the top of the Caddyfile, backed by a
  `./caddy-sites` bind mount. **Other projects' configs live outside this repo**
  and survive every deploy. Verified against `caddy:2-alpine` that an import
  matching **zero** files still validates - otherwise adding this would have
  taken takeoff down on a box with an empty directory.
- `web-proxy` as an **external** network on the caddy service, declared in
  compose rather than attached live, so a recreate cannot lose it. External so
  tearing down this stack cannot delete another project's network.

Applied at 03:20 with nobody logged in. **The app container was not touched**
(up 27 hours through the change); only Caddy was recreated, ~2 s. Verified
after: 303 to login, `/terms` 200, and a certificate that still validates
without `-k`.
