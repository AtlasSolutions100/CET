## F67 — Bill's coloured markings are an ANSWER KEY, not a feature to detect

Koby clarified that "Marked Up Window Plans - Aqua Vista" is Bill demonstrating his
own estimating method. Verified on the sheet: the cyan swipe sits **on a printed
hexagonal `W1L` callout** that the architect drew. At 2200% (`tag_zoom.png`) the tag
reads `W1L` unambiguously and his highlighter sits **below** the glyphs, so it does
not obstruct OCR. Tag geometry is roughly 9x10 pt on a 792x1224 page.

An earlier hypothesis that colour keyed one swipe per window is **disproved**:
distinct cyan blobs per floor are 9/24/11/2/6 against a tally of 28/33/29/29/29.
Colour keys the *type* in his notation; it does not count openings, so blob-counting
is not a valid proxy.

**Consequence:** build a printed-tag detector, not a highlighter detector. Pages are
pure raster (one 3300x5100 JPEG at 300 dpi, zero text objects), so this is symbol
detection + OCR, not text extraction.

## F69 — The output contract for this trade is a per-type QUANTITY

`TakeOff sent to Supplier - Windows and Balcony Doors.pdf` is what Bill delivers: a
faxed QUOTE REQUEST to Sonora Valley Window Works, from Bill Dunn. The architect
preprints a grid of type elevations (dimensions, `FIXED`/`SCREEN` panel labels, swing
arcs, the same hexagon tag as the plans) and Bill hand-writes **one quantity per type**
("19 each") plus **`T` marks on the individual panes needing tempered glass**.

Full loop: tags on plans -> per-floor tally -> per-type quantity on the schedule ->
fax to supplier.

**Counts alone are not a sendable deliverable.** Output must be a per-type quantity
keyed to the architect's own type codes.

**Open for the client (do not guess, CLAUDE.md §4):** the `T` marks are per-pane, so
two windows of one type could need different panes tempered depending on location.
Ask whether tempering is decided per type or per opening — that decides whether a
per-type quantity is complete output or whether location must also be reported.

## F70 — `Window - Storefront - Door schedules.pdf` is a DIFFERENT project, and is vector

Its types are letters A-Z under "WINDOW TYPES: RESIDENTIAL" and "PODIUM EXTERIOR
STOREFRONT"; it contains **no W-codes at all**. It is the schedule for the same job as
the supplier quote requests, not for Aqua Vista. Aqua Vista's own schedule is page
index 0 of the marked-up set. Do not use it as the type dictionary for Aqua Vista.

Separately: it is the **only vector PDF Bill sent** (11,838 / 9,603 / 11,616
extractable chars across 3 pages, 1224x792, unrotated). Every other file of his is a
300-dpi raster scan. Where a schedule arrives in vector form the table is directly
extractable, which is far cheaper and more reliable than OCR.
